# Skill: 改动自查与 PR 描述

## 何时用

- 测试已经通过，需要收尾、生成 patch / PR 描述；
- 想确认这次改动"只修了该修的"。

## Workflow

1. **看 diff**：`git_diff` 拿到 unified diff（没有 git 时工具会退回与 `*.orig` 快照对比）。
2. **逐条自检**：
   - 改动是否只落在源码文件上？**测试文件一行都不该动**；
   - 是否引入了无关的格式变动（整段缩进、行尾空格、删注释）？
   - 修复是否可解释：diff 里每一行都能说清"为什么改"？
3. **写一句话补丁说明**，模板：

   ```
   修 <文件>:<函数> —— <症状>，改为 <正确做法>。测试 <通过/失败>。
   ```

4. **没通过就别写"已完成"**：报告里如实写清哪一步失败、卡在哪里。

## 输出建议

PR 描述控制在 3~6 行：问题现象、根因、改动、验证方式。不要复述整份 diff。
