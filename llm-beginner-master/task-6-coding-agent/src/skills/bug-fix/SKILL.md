# Skill: 最小化 Bug 修复

## 何时用

- issue 明确点名一个函数/方法要修（"修复 `calculator.add` 的实现"）；
- 测试失败但报错点收敛在少数几个函数上。

## Workflow

1. **先复现**：跑一次测试，把失败用例与断言差异记下来（见 test-runner skill）。
2. **读源码**：`read_file` 打开嫌疑文件，**不要凭函数名猜实现**，一定把原文读出来。
3. **对照语义找 bug**：拿函数 docstring / 函数名 / 测试断言三者对齐。
   典型病症：
   - 运算符写错：`a - b` 应为 `a + b`；
   - 边界写反：`<` 应为 `<=`，`range(n)` 应为 `range(n + 1)`；
   - 变量写错：累乘写成累加。
4. **最小改动**：优先 `edit_file(old, new)` 只替换出错的那一小段，不要整文件重写。
   `old` 必须与文件里的原文逐字一致（含缩进），否则工具会拒绝执行——这是刻意的，
   防止"以为改了其实没改"。
5. **验证**：改完立刻 `run_tests`。只有真实输出显示通过才算完成。
6. **确认没越界**：不要动测试文件、不要改无关代码。

## 反模式

- 猜实现就动手改，结果把没坏的代码改坏；
- 一次改很多处，失败了分不清是哪一处引起的；
- 用 `write_file` 覆盖整个文件（除非改动确实遍布全文）。
